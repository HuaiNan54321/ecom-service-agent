前面几期，小夕是一个全能客服——同一个 system prompt、同一套工具、什么问题都接。能跑通，但问题也明显：售前要热情推荐、售后要耐心排查、投诉要先安抚再处理，这些风格塞进一个 prompt 会互相打架，工具也全暴露给模型，查退款的时候它可能顺手去搜商品推荐



## 路由 + 专家分治

这期的核心设计是 Router-SubAgent 模式。用户说话后，先过一个轻量 Router 做意图分类（presale / postsale / complaint），然后把请求交给对应的子 Agent 处理

Router 本身也是一次 LLM 调用，但只要求输出一个词，temperature=0，max_tokens=10，延迟和成本都很低。它还会看最近 4 轮对话做上下文，避免用户说"那退货呢"被误判成新会话

每个子 Agent 拥有独立的三样东西：专属 system prompt（定义人设和回复风格）、工具子集（售前只能搜商品，投诉只能查订单）、独立的 ReAct 循环。工具隔离是通过 ToolManager 的 allowed_tools 白名单实现的，初始化时就过滤掉不该用的工具



## 为什么不用 if-else 路由

意图分类看起来可以用关键词匹配或规则引擎做，为什么要用 LLM？

因为自然语言的模糊性。"这个质量也太差了吧"是投诉还是售后？"买了三天了还没发货我很不满"是物流问题还是投诉升级？这些边界只有语义理解能处理好。用 LLM 做路由，后续增加新的子 Agent 也只需要改 prompt 里的分类描述，不用写新规则

这也是 Multi-Agent 比 Single-Agent 更适合复杂场景的原因——每个子 Agent 可以深耕一个领域，prompt 更聚焦，工具更精简，模型幻觉更少



## 编排器的角色

Orchestrator 是整个系统的协调者。它不处理具体业务，只负责：接收用户输入→调 Router 路由→选子 Agent 执行→结构化提取结果→管理对话历史和摘要压缩

对话记忆是共享的。用户先问售前再问售后，上下文不会丢。摘要压缩逻辑复用了之前做的 summarizer，超过阈值就把老消息压成 summary 注入新对话
